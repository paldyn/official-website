Main additions of 11 November 2026

  • GitHub and GitLab account connections: only if you connect an account with a personal access token in Settings → Accounts & integrations, Branch reads from that service, without your asking and at intervals, the pull or merge requests of the current local branch and the CI results of commits while the commit history of a repository whose remote address points to that service is open. These requests carry the access token, the repository's path on that service, the local branch name and commit IDs. Opening Settings → Accounts & integrations also loads the account's profile photo. The token is stored in the login keychain on macOS or in Windows Credential Manager on Windows and sent only to that service; disconnecting the account stops these reads and deletes the token. Deleting Branch does not delete the token, so disconnect first or delete it in Keychain Access on macOS or Credential Manager on Windows. (Sections 7.2 to 7.5 and 10.3)
  • Drone CI connection: only if you connect a Drone server in Settings → Accounts & integrations with its address and an access token, Branch sends requests to it, and only to /api at that address. While the "Drone CI" window is open, it reads the builds again every 10 seconds while one has not finished, and whenever the current branch or the names or addresses of the remotes change; it runs or re-runs a build only after you confirm. The token is stored and deleted like the account tokens and sent only to that server. With an http:// address, the token and the server's answers travel unencrypted, so use an https:// address whenever you can. (Sections 7.2 to 7.5 and 10.3)
  • Choice of external terminal: Branch opens repositories in the terminal you choose under External terminal in Settings → External apps (Terminal on macOS and Windows Terminal on Windows unless you choose another) and keeps that choice with your settings. (Section 7.4, item 1, and Section 7.5)
  • Automatic Bisect tests and verdict correction: when you review the test program you chose and confirm the run, Branch runs that program with your permissions in the working folder where each commit to test is checked out; what the program does is not determined or limited by Branch. The test record (up to the newest 100 runs) is deleted when you end the Bisect session in Branch, but the Bisect logs kept from before and after a verdict correction are never deleted automatically and cannot be deleted in Branch, so delete them yourself when you no longer need them. (Section 7.4, items 12 and 13, and Section 7.5)
  • Worktree registration archive: when you clean up the registration of a worktree whose folder is missing, Branch moves what Git recorded for that worktree (such as its current branch, its index and the reflog with author names, email addresses and commit messages), together with its discard recovery copies and Bisect records, into branch/worktree-archives/ in the repository's common Git folder instead of deleting them (up to 32 registrations). They remain with no time limit until you restore the registration or delete them yourself, and Branch has no command to delete the archive. (Section 7.4, items 10 and 14)
  • Git LFS locks and history conversion: listing, setting and releasing Git LFS locks connect to the remote only when you ask. When Branch creates a new branch from a Git LFS history conversion, it keeps the commit that the source branch points to as a recovery checkpoint. (Section 7.3 and Section 7.4, item 5)
  • Commit message templates: the path of the template file you choose is written to commit.template in your Git configuration only when you save it, and Branch reads that file on your device to preview it. (Section 7.4, item 3)
  • Custom actions: the actions you register in Settings → Custom actions (up to 50) are stored on your device and included in settings backups, but importing a backup never runs them. When you choose an action in the menu of a repository, a branch or a file, Branch shows the program, its arguments and its working folder, asks you to confirm every run and only then runs the program with your permissions (for up to 30 minutes). The result is kept in the activity history, and what the program does is not determined or limited by Branch. (Section 7.4, items 8 and 15, and Section 7.5)
  • Saved commit searches: the searches you save in the "Saved commit searches" window of the commit history (up to 30 per repository) are stored on your device, without their results. They remain with no time limit until you delete them in that window, even after you close the repository or remove it from the list, and they are included in settings backups. (Section 7.4, item 16)
  • Update checks while Branch runs: with "Automatically check for updates" on in Settings → Updates (the default), Branch checks for a new version 30 seconds after it starts and every 24 hours while it runs, instead of when it starts. (Section 6.2, item 1)
  • Temporary folders of the new features: for a Git LFS history conversion, a synchronization of submodule addresses, the conflict check of the cherry-pick, revert, rebase and interactive rebase dialogs, an import of commit patches and saving or deleting a commit note, Branch keeps the repository contents and files the work needs in the operating system's temporary folder and deletes them when the work ends. If Branch quits during the work, they can remain in that folder. (Section 7.5)
  • Also: a recovery checkpoint is now also recorded before an import of commit patches, and repository settings you change and confirm in Branch, such as remotes, upstream branches and submodule addresses, are written to that repository's configuration. When Branch updates submodules, it checks out the recorded commits instead of following the update mode in the repository configuration, and when it synchronizes submodule addresses, an address in .gitmodules that contains credentials may be recorded in the repository configuration. (Section 7.3 and Section 7.4, items 3 and 5)

Of these, GitHub and GitLab account connections, custom actions, saved commit searches and the update checks while Branch runs are not offered before the effective date. The Drone CI connection is offered from 12 November 2026 to users who agree when connecting, as set out in the further notice above.

Ordinary request information, such as your IP address, the time of the request, and the web view's identification string (User-Agent) and language preferences, reaches GitHub or Automattic with each request and is handled under their privacy statements, so these services can tell which commit authors are being viewed from your connection. Turning off "Author photos" in Settings → Appearance stops these requests. When you connect a GitHub or GitLab account with a personal access token in Settings → Accounts & integrations, the Software sends requests carrying that token over HTTPS to that service's API (for GitHub, api.github.com; for GitLab, /api/v4 at the GitLab server address you enter). Besides connecting or checking an account and opening the list of repositories to clone, while the commit history of a repository whose remote address points to a connected account's service is open (the commit history is the first view, so this includes right after the Software starts), the Software reads, without any further request, the pull or merge requests of the current local branch and the CI results (GitHub Actions runs or GitLab pipelines) of the selected commit, the current commit and the commits shown on screen (up to 80) ("Git service status reads"). While the window is visible, it reads pull and merge requests, the current commit's CI results and CI results still in progress again every minute and finished CI results every 15 minutes, and it reads the CI results of commits that newly come into view right away. These requests carry the access token, the repository's path on that service, the name of the local branch, which may not have been pushed, and commit IDs; they follow the operating system's proxy settings and, together with ordinary request information such as your IP address and the time of the request, are handled under that service's terms and privacy statement. Disconnecting the account stops Git service status reads. When you open Settings → Accounts & integrations, the Software also loads each connected account's profile photo, without credentials, from the address the service gave (for GitHub, avatars.githubusercontent.com; for GitLab, that server or Gravatar). These requests do not depend on the "Author photos" setting. The photos are not saved to files; so as not to request the same photo again, the Software keeps it in memory for up to 10 minutes while it runs. When you connect a Drone server in Settings → Accounts & integrations by entering its address and an access token, the Software sends requests carrying that token only to /api at the Drone server address you entered. These requests are made when you connect the server or check the connection, when the "Drone CI" window opens and reads the list of Drone repositories, when it reads the details and recent builds of the repository chosen in that window (a Drone repository that matches a remote of the current repository can be chosen by itself when the window opens), and when you run or re-run a build after confirming it. While the "Drone CI" window is open, the Software also, without any further request, reads that repository's details and recent builds again every 10 seconds while one of the recent builds it shows has not finished and, when the current branch or the names or addresses of the current repository's remotes change, reads the list of Drone repositories and the details and recent builds of the repository chosen by itself again, as when the window opens ("Drone build reads"). These requests carry the access token and the repository's path on the Drone server and, when you run a build, the branch name you confirmed or, when you re-run one, its build number; they follow the operating system's proxy settings and, together with ordinary request information such as your IP address and the time of the request, are handled under the policies of whoever operates that Drone server. The Software does not follow answers that send a request to another address (redirects), and it sends none of these requests or answers to PALDYN. If the server address starts with http:// rather than https://, the requests, which carry the access token, and the Drone server's answers travel unencrypted, so a third party on the network path can intercept the token or change the answers. Use an https:// address whenever you can. Disconnecting the Drone server stops Drone build reads.
  3. Git remote operations. Git remote operations, such as cloning, fetching, pulling, pushing, listing remote references (including the connection check in Settings → Git), adding or updating submodules, downloading Git LFS content and listing, setting or releasing Git LFS locks, run only when you request them, except for the automatic Fetch described at the end of this paragraph. The Software performs them by running a Git program (the Git included with the Software or, if you choose it in the settings or the included Git cannot run, the Git installed on your computer) and connects only to remote addresses that you enter or choose or that are configured in the repository, including submodule addresses. The permitted transports are file, https, http, ssh and git. Authentication is handled by your Git configuration, SSH keys and credential helpers; the Software itself does not store passwords, tokens or other credentials, except the access tokens of the Git service accounts and of the Drone server described at the end of paragraph 2. It stores those access tokens in, and reads them from, the login keychain on your computer on macOS (service name com.paldyn.branch.hosting, one item per account or Drone connection, a Drone server's token in the item whose account name starts with drone:) and Windows Credential Manager on Windows (generic credentials whose names start with com.paldyn.branch.hosting:, a Drone server's token in the one whose name starts with com.paldyn.branch.hosting:drone:, kept on this computer only), and sends each Git service account's token only to its Git service and the Drone server's token only to the Drone server address you entered. When you clone a repository chosen from a connected account, or check the connection for that clone, the Software authenticates with that access token itself: it uses no Git credential helper (including Git Credential Manager on Windows), shows no sign-in window or prompt, and passes Git, through Git's environment, an authorization header that applies only to that repository's address. The hooks and filters that Git operation runs receive that environment too. When the included Git is used on macOS, the macOS keychain credential helper of Git that is included with the Software is configured by default (your Git configuration can replace it). Like the helper of Apple's Git, it stores the HTTPS credentials with which Git has signed in successfully in the login keychain on your computer and reads them from there. On Windows, the Git Credential Manager contained in the Git included with the Software is configured as the default credential helper (your Git configuration can replace it). When a remote operation (other than a clone from a connected account or its connection check) needs HTTPS authentication, Git Credential Manager uses the sign-in information it has stored (refreshing or checking it when needed) and, for a remote operation you requested, runs the remote service's sign-in in your default browser or in its own window; in doing so it may also connect to the addresses that service uses for sign-in and authentication (for example GitHub's API address, or the Microsoft account sign-in address for Azure DevOps). Git Credential Manager stores the sign-in information (tokens or passwords) in Windows Credential Manager on your computer and reads it from there, the same store that the Git Credential Manager of a Git for Windows installed on your computer uses. On either operating system, these credentials are not sent to PALDYN. If you include credentials in a remote address, however, or a submodule address in .gitmodules contains them, Git or the Software (when it synchronizes submodule addresses) may record that address in the repository configuration. Information exchanged with a remote service (for example GitHub, GitLab, Bitbucket or Azure DevOps) is subject to that service's terms and privacy statement. Git behaves as your Git and repository configuration directs, for example when running Git hooks or when Git automatically downloads missing objects in a partial clone. When the Software updates submodules, however, it checks out the recorded commits instead of following the update mode in the repository configuration (merge, rebase or a command in submodule.<name>.update), and it checks out a submodule whose update mode is none only when you choose that submodule to update. This includes checking the signatures of commits and tags: when the details of a signed commit are shown in the commit history or you open the signature check of a tag, the Software has Git run, on your device, the signing program set in your Git configuration (unless you set another, GnuPG's gpg for OpenPGP signatures and ssh-keygen for SSH signatures) to check the signature. Because the Software selects the current commit automatically when a repository opens and after operations such as switching branches, this check can take place without your choosing a commit. The Software adds no communication of its own to this check, but depending on your GnuPG configuration (for example auto-key-retrieve or key server settings), GnuPG may connect to a key server or a similar service to find the signer's public key. The Software re-reads repository status periodically, and when it notices changes in the folder of the repository you are viewing, to keep its display current, but it does not run Git commands that contact remote repositories, such as fetch, for this purpose. However, when you choose an interval for "Automatic Fetch" in Settings → Git (it is "Off" by default, and the intervals range from 1 to 60 minutes), the Software, while it is running and without any further request, fetches at that interval from all remote repositories configured in each repository that is open in the current workspace and for which automatic Fetch has not been turned off, one repository at a time (git fetch --all --prune; "automatic Fetch"). Automatic Fetch connects only to the remote addresses configured in those repositories (including, when a credential helper such as Git Credential Manager refreshes or checks a saved sign-in, the addresses that remote service uses for sign-in and authentication), uses only credentials that are already saved, and the Software shows no sign-in window or prompt for it. macOS may, however, ask whether to allow access the first time the included Git reads credentials that another Git saved in the keychain, and credential helpers or SSH agents that you set up yourself may ask for confirmation as you configured them. If a remote service rejects a saved sign-in, Git may have the credential helper delete that sign-in, also during automatic Fetch, and the deleted item may be one that other Git apps use as well (in the login keychain on macOS, or in Windows Credential Manager on Windows). A remote repository that needs a new sign-in is not fetched automatically, and the failure is recorded in the Activity center. Automatic Fetch does not change your working files or local branches; it updates remote-tracking branches (removing those of branches deleted on the remote) and may add tags that point to fetched commits. Choosing "Off" for "Automatic Fetch" in Settings → Git stops automatic Fetch, and a repository you untick in the list there is not fetched automatically.
  4. Information stored on your device. The Software stores the following information only on your device and does not send it to PALDYN:
    1. settings (such as theme, accent color, language, keyboard shortcuts, the update settings, the external editor you chose, which is an application name or the path of an application you selected, the external terminal you chose, the comparison and merge tools you chose, the automatic Fetch interval and the path of the default work folder in which the Software looks for repositories), workspace information (local paths of the repositories you opened, tabs, groups and, for repositories brought over from a backup, their remote addresses), the version and release notes of an Update recorded right before it is installed (used to show release notes after the restart; this temporary entry is deleted once shown or no longer needed), the most recently installed version's release notes retained for reopening in Settings regardless of the automatic-popup setting (replaced by the next installed version's notes and excluded from backups), and, for each repository, commit message drafts in progress, layout, the order of local branches, the names of recently used local branches, whether automatic Fetch is on, the name of the branch to return to after you check out a specific commit, and the commit ID at which a detached HEAD began: in the local storage of the Software's built-in web view (on macOS, ~/Library/WebKit/com.paldyn.branch/; on Windows, %LOCALAPPDATA%\com.paldyn.branch\EBWebView\);
    2. window position and size, the choice of Git executable, the system-level Git configuration generated for the included Git, the settings snapshots saved automatically with the current settings before a backup is imported or earlier settings are restored (the newest 5 are kept), the practice repositories created by the guides, the Git service accounts you connected (the service, server address, the account's user ID, login and display name, profile photo address and when it was checked; excluded from settings backups) and the Drone server you connected (the server address, login, connection ID, when it was last checked, when you gave the agreement under paragraph 3 of the Effective date section, the effective date of the provisions you agreed to and the default Drone repository you set for each repository; never the access token, and excluded from settings backups): in .window-state.json, git-executable.json, bundled-git/gitconfig, backups/, practice/, hosting-accounts.json and drone-connection.json in the application settings folder (on macOS, all in ~/Library/Application Support/com.paldyn.branch/; on Windows, .window-state.json in %APPDATA%\com.paldyn.branch\ and the rest in %LOCALAPPDATA%\com.paldyn.branch\);
    3. Git settings values: your Git author name and email, the signing settings for commits and tags (gpg.format, user.signingkey, commit.gpgsign, tag.gpgsign, gpg.ssh.allowedSignersFile), the pull method (pull.rebase) and the commit message template (commit.template, the path of the template file you chose; the Software reads that file's contents on your device to preview it), written to your Git configuration (global or for the repository) only when you save them in the Software. Repository settings you change and confirm in the Software, such as remotes, upstream branches (branch.<name>.remote, branch.<name>.merge) and submodule addresses (submodule.<name>.url), are written to that repository's configuration too. When you set up Git LFS in a repository, the Software writes the Git LFS settings (filter.lfs.* and lfs.repositoryformatversion) to that repository's configuration and, if the repository's Git folder has no hooks/pre-push, creates Git LFS's pre-push hook, which uploads Git LFS content when you push; when you add or remove a Git LFS tracking rule, it edits the .gitattributes file at the top of the repository (like any other file, it reaches remote repositories when you commit and push it). So that you can choose a signing key, the Software reads, on your device, the names of the public key files (.pub) in your ~/.ssh folder (on Windows, %USERPROFILE%\.ssh\); it records a name, as the user.signingkey above, only when you choose that key as your signing key and save it, and it never sends the key files' names or contents;
    4. temporary working files needed for an interactive rebase: inside that repository's .git folder;
    5. recovery references: before a reset, a rebase, an interactive rebase or an import of commit patches (Git mailbox patches applied as commits), the Software records the commit that HEAD points to, and before it deletes a branch or tag in a remote repository, it first fetches the commit or tag that the remote branch or tag points to. Before a force push, it records the remote commit confirmed for replacement, and when it creates a new branch from a Git LFS history conversion, the commit that the source branch points to. It keeps each of these in that repository as a Git reference under refs/branch/recovery/, with a reflog entry, so that the previous state can be recovered. When a new checkpoint is created, the Software keeps the newest 20 references it can identify as its own or those created less than 14 days ago; older references that satisfy neither condition are eligible for automatic cleanup. It does not automatically delete references used by active sessions or references it cannot identify as created by the Software, and it skips cleanup if it cannot read session information from any worktree of the repository. Some references may therefore remain longer. You can also delete them yourself, for example with git update-ref -d <reference name>, or all at once with git for-each-ref --format='delete %(refname)' refs/branch/recovery/ | git update-ref --stdin. While they remain, Git's garbage collection does not remove the commits they point to, even after a reset has removed those commits from your branches. Ordinary pushes and clones do not transfer these references, but commands that copy every reference of a repository, such as git push --mirror or git clone --mirror, do;
    6. if settings saved under the identifier of an earlier version exist, the Software copies them to the new location on your device the first time it runs;

When you preview or import commit patches (including when you continue or skip a paused import or a paused rebase that applies patches, git rebase --apply), it keeps copies of the commit patches in a folder whose name starts with branch-mailbox-, and when you save or delete a commit note, a Git index file listing the notes in a folder whose name starts with branch-commit-note-, both in that temporary folder, and it deletes them when the work ends.
