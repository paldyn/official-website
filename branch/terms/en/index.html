Notice of changes to these terms

On 11, 12, 17, 24 and 25 November 2026 we supplemented the amended Agreement announced on 3 November 2026 with provisions on the features added since. The amended Agreement on this page still takes effect on 1 January 2027. The provisions on the GitLab CI connection and on the changed Drone CI connection, however, take effect on 24 November 2026, and those on connecting GitHub, GitLab and Gitea accounts on 25 November 2026, and they apply to a user from the time the user agrees to them (Effective date, paragraphs 4, 5 and 7). Further notice of 25 November 2026: creating, merging and closing pull and merge requests

We added merging, closing and reopening pull requests (on GitLab, merge requests, as in the rest of this notice) and creating them on GitHub and GitLab to the provisions of the amended Agreement on connecting GitHub, GitLab and Gitea accounts. They take effect on 25 November 2026 and apply to users who agreed to account connections. For a user who agreed before they were added, they apply to an operation from the time the user confirms it in Branch (to reading the pull request and its repository's details in order to merge, from the time the user chooses "Merge…"), and Branch sends no request for that operation before that. This is available from the update that contains this change. The earlier text is in the amended Agreement before the provisions on creating, merging and closing pull and merge requests of 25 November 2026. The effective date of the rest of the amended Agreement (1 January 2027) and the agreements needed for account connections, GitLab CI and Drone CI do not change. (Effective date, paragraph 7)

  • Creating: Branch creates a pull request only after you choose its target branch and write its title and description in the GitHub, GitLab or Gitea tab and confirm them with "Create pull request" (on GitLab, "Create merge request"; on Gitea, as before), and then sends that service the access token, the repository's path on that service, the names of the two branches, the title and the description. (Section 7.2)
  • Merging: when you choose "Merge…" for an open pull request in that tab, Branch reads that pull request and its repository's details (including the merge methods it allows, whether branches are deleted after a merge by default or by itself and your permission) from that service and shows them, and it asks for the merge only if you then choose "Merge" with them in view. It then sends that service the access token, the repository's path on that service, the number of the pull request, the merge method you chose, the ID of the last commit shown and (except on GitHub) whether to delete the source branch after the merge. If it receives no answer that the merge was done, it reads that pull request once more to check. (Section 7.2)
  • Closing and reopening: Branch does this only after you confirm it in that tab, and sends that service the access token, the repository's path on that service, the number of the pull request and the new state. (Section 7.2)
  • Where it is sent and what changes: Branch sends this to api.github.com for GitHub, to /api/v4 at the connected server for GitLab and to /api/v1 at the connected server for Gitea. A merge changes the target branch on that service and, on GitLab and Gitea, if you chose so, deletes the source branch there. On GitHub, Branch does not delete the source branch when it merges; if the repository is set to have it deleted after a merge, GitHub deletes it under that setting. The results of creating, merging, closing and reopening stay on that service and are handled under the terms and policies of whoever operates it (on GitLab and Gitea, that server). (Section 7.2)
  • The Fetch after merging: after a merge, Branch fetches that repository once, even if you turned automatic Fetch off or left that repository out of it. Like automatic Fetch, it connects only to the remote addresses configured in the repository (including, when a saved sign-in is refreshed or checked, the addresses that remote service uses for sign-in and authentication), uses only sign-ins that are already saved, shows no sign-in window and does not change your working files or local branches. (Sections 7.2 and 7.3)
  • The GitHub tab: in versions that show the GitHub Actions panel as the "Actions" view of the GitHub tab, that view is the GitHub Actions panel, and moving to another view of that tab counts as closing it. What is read and sent does not change. (Section 7.2)
  • Branch names: on GitHub and GitLab, the requests that read the pull requests of the current local branch carry, if that branch was pushed to that remote under another name, that name in place of the local branch's. (Section 7.2)
  • What does not change: nothing changes for users who have not agreed to account connections, and nothing is sent to PALDYN. What concerns the "Actions" view of the GitHub tab and branch names adds no request, so it applies from 25 November 2026 also to users who already agreed. (Section 7.1 and Effective date, paragraph 7)

Further notice of 25 November 2026: automatic Fetch on by default

We changed the provisions of the amended Agreement on automatic Fetch again: automatic Fetch is on by default, and the notice that asked for an agreement is gone. They take effect on 25 November 2026 and apply to every user on macOS and Windows without a separate agreement. Branch works as described below once you install an update with this change; earlier versions of Branch fetch only if you agreed in the notice or chose an interval in Settings → Git. The earlier text is in the amended Agreement before the automatic Fetch change of 25 November 2026. The effective date of the rest of the amended Agreement (1 January 2027) and the agreements needed for Drone CI, GitLab CI and account connections do not change. (Effective date, paragraph 6)

  • The default: unless you turn it off, Branch fetches the repositories open in the current workspace when it starts and then, while it is running, every 10 minutes. You can change the interval to between 1 and 60 minutes in Settings → Git. (Sections 7.2 and 7.3)
  • Turning it off: choosing "Off" for "Automatic Fetch" in Settings → Git at any time stops all of it, including the Fetch at start, and you can turn it off for a single repository there. For the Fetch after merging a pull or merge request, see the further notice above. (Section 7.3)
  • What you already chose: if you chose "Off", it stays off. If you chose an interval or brought one with a settings backup, Branch uses that interval and also fetches when it starts; if you chose "Keep it as it is" in the automatic Fetch notice, however, it does not fetch at start until you choose something else in Settings → Git, import a settings backup that contains that setting or go back to earlier settings that contain it. (Effective date, paragraph 6)
  • What does not change: automatic Fetch connects only to the remote addresses configured in your repositories (including, when a saved sign-in is refreshed or checked, the addresses that remote service uses for sign-in and authentication), uses only sign-ins that are already saved, shows no sign-in window and does not change your working files or local branches. Nothing is sent to PALDYN. (Sections 7.1 and 7.3)
  • Information stored on your device: your choice in the automatic Fetch notice is no longer stored. What was already stored may remain on your device until you choose something else for "Automatic Fetch" in Settings → Git, import a settings backup that contains that setting or go back to earlier settings that contain it, and it is left out of settings backups. (Section 7.4.1 and Effective date, paragraph 6)

We brought forward the effective date of the provisions of the amended Agreement on connecting GitHub and GitLab accounts (including the GitHub Actions panel) and added connecting Gitea accounts. They take effect on 25 November 2026 and apply to a user from the time the user agrees to them in Branch when connecting an account (or, for an account already connected, when Branch asks for that agreement). Before that agreement Branch sends no request to GitHub or to a GitLab or Gitea server through an account connection, and for users who connect no account nothing changes except that screens on account connections, such as the GitHub Actions, GitLab and Gitea tabs on the right, appear. For users who do not agree, the earlier provisions that apply to them under paragraph 2 of the Effective date section apply (those on connecting GitHub and GitLab accounts in the amended Agreement before the changes of 24 November 2026; for macOS users before 1 January 2027, the Agreement of 20 October 2026). The effective date of the rest of the amended Agreement (1 January 2027) does not change. (Effective date, paragraph 7)

  • Where requests go: when you connect an account with a personal access token in Settings → Accounts & integrations, Branch sends requests carrying that token over HTTPS to api.github.com for GitHub, to /api/v4 at the server you enter for GitLab and to /api/v1 at the server you enter for Gitea. When you clone a repository chosen from a connected account, Branch signs in to that repository's address with the token. Nothing is sent to PALDYN. (Sections 7.1 to 7.3)
  • What is read without your asking: while the commit history of a repository whose remote address points to a connected account's service is open, Branch reads the pull or merge requests of the current local branch and the CI results of the commits shown. It reads pull and merge requests, the current commit's CI results and unfinished CI results again every minute and finished CI results every 15 minutes. These requests carry the access token, the repository's path on that service, the local branch name (not sent to Gitea) and commit IDs; the branch and the commits may not have been pushed. "Merge requests" in the GitLab tab on the right and the Gitea tab show what was read this way. For what was added on branch names on 25 November 2026, see the further notice above. (Section 7.2)
  • The GitHub Actions panel: opening it reads the target repository's workflows and recent runs and the current branch's pull requests, and while it is open and a run has not finished, Branch reads the recent runs again every 10 seconds. It reads again when the current branch changes or the target repository changes (also because you connect, disconnect or agree to a GitHub account). Dispatching, re-running or cancelling a run is sent only after you confirm it. For the "Actions" view of the GitHub tab, see the further notice of 25 November 2026 above. (Section 7.2)
  • Gitea: Branch reads the repository's latest pull requests (up to 30), picks out those of the current local branch and reads the CI results of the last commit of the open ones every minute, too. It creates a pull request only after you choose its target branch and write its title and description in the Gitea tab and confirm them with "Create pull request", and then sends the names of the two branches, the title and the description to that server. For merging, closing and reopening and for creating on GitHub and GitLab, added on 25 November 2026, see the further notice above. (Section 7.2)
  • Profile photos: opening Settings → Accounts & integrations loads the profile photos of connected accounts, without the token, from the address the service gives. They are not saved to files. (Section 7.2)
  • Information stored on your device: the token is stored in the login keychain on macOS or in Windows Credential Manager on Windows, and the account's information, the time you agreed and the effective date of the provisions you agreed to are kept in hosting-accounts.json in the application data folder. All of it is left out of settings backups. Disconnecting the account stops the reads and deletes the token and the account's information. Deleting Branch does not delete the token, so disconnect first. (Section 7.3 and Section 7.4, items 2 and 11)
  • Names and logos: Gitea joins the names and logos that are trademarks of their owners and are used only to identify a service. The GitHub Actions, GitLab and Gitea tabs on the right and gitea.com remotes show the service's logo whether or not you agree, and the GitLab tab also shows GitLab CI's pipelines. (Section 10.3 and Effective date, paragraph 7)

Further notice of 24 November 2026: the GitLab CI connection and changes to the Drone CI connection

We added provisions on the GitLab CI connection to the amended Agreement and changed those on the Drone CI connection. Both take effect on 24 November 2026 and apply to a user from the time the user agrees to them when making that connection (or, for a Drone server connected before, when Branch asks again). The effective date of the rest of the amended Agreement (1 January 2027) does not change. (Effective date, paragraphs 4 and 5)

  • GitLab CI connection: when you connect a GitLab server under GitLab CI in Settings → Accounts & integrations with its address and an access token, Branch sends requests carrying the token only to /api/v4 at that address. It is separate from a GitLab account connection. The "GitLab CI" window reads the details, branch list and recent pipelines of the default project or of the project that matches a remote, and while it is open it reads the pipelines again every 10 seconds while one has not finished. Pipelines are run, retried and cancelled only after you confirm it. The token is stored in the login keychain on macOS or in Windows Credential Manager on Windows, sent only to that server, left out of settings backups and deleted when you disconnect. With an http:// address, the token and the server's answers travel unencrypted, so use an https:// address whenever you can. (Sections 7.2 to 7.5)
  • After the window closes: if a build or pipeline has not finished when you close the "Drone CI" or "GitLab CI" window or move to another repository, Branch reads it again every 10 seconds only until it has finished, to keep the toolbar and the commit history current. If nothing was running, nothing is read for that repository until the window shows it again (a read already started may be finished). (Section 7.2)
  • Sending a commit: when the pipeline you run is in another repository, or you choose a commit to send, Branch also sends the commit ID of the current repository (the commit may not have been pushed yet) as BRANCH_SOURCE_COMMIT (a build parameter for Drone, a pipeline variable for GitLab), and uses only that value of the builds and pipelines it reads, to show it with them in the window and to show their status on that commit. The confirmation shows the commit, which you can change there or in the commit history's menu. The commit ID sent stays on the server with the build or pipeline. (Section 7.2)
  • Agreeing again to the Drone CI connection: the two points above, the reading of the branches Drone has built and the reads when a connection changes join the Drone CI connection. Users who connected a Drone server before must agree again; until then the earlier provisions apply to them and the new version of Branch sends nothing to the Drone server. (Effective date, paragraph 5)

When you choose an action in the menu of a repository, a branch or a file, Branch shows the program, its arguments and its working folder, asks you to confirm every run and only then runs the program with your permissions (for up to 30 minutes).   • Temporary folders of the new features: for a Git LFS history conversion, a synchronization of submodule addresses, the conflict check of the cherry-pick, revert, rebase and interactive rebase dialogs, an import of commit patches and saving or deleting a commit note, Branch keeps the repository contents and files the work needs in the operating system's temporary folder and deletes them when the work ends. If Branch quits during the work, they can remain in that folder. (Section 7.5)
  • Also: a recovery checkpoint is now also recorded before an import of commit patches, and repository settings you change and confirm in Branch, such as remotes, upstream branches and submodule addresses, are written to that repository's configuration. When Branch updates submodules, it checks out the recorded commits instead of following the update mode in the repository configuration, and when it synchronizes submodule addresses, an address in .gitmodules that contains credentials may be recorded in the repository configuration. (Section 7.3 and Section 7.4, items 3 and 5)

Of these, custom actions, saved commit searches and the update checks while Branch runs are not offered before the effective date.
