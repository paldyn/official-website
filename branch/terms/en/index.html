Notice of changes to these terms

We have amended this Agreement to cover Branch for Windows and the features added since. The amended Agreement on this page takes effect on [[REVISION EFFECTIVE DATE]].

  • Branch for Windows: the amended Agreement applies from the time you install or use it.
  • Branch for macOS: the Agreement of 20 October 2026 continues to apply until that date.

What changed

  • Windows support: the Agreement applies to Branch for macOS and for Windows, and states what differs on Windows, such as where information is stored, the included Git (MinGit, Git LFS and Git Credential Manager) and how sign-ins are stored, and the Microsoft Edge WebView2 Runtime. (Sections 1, 7 and 10)
  • Automatic Fetch: only if you choose an interval in Settings → Git (it is Off by default), Branch fetches the repositories open in the current workspace at that interval while it runs. You can turn it off for each repository; it uses only sign-ins that are already saved and does not change your working files or local branches. (Sections 7.2 and 7.3)
  • Information stored on your device: the activity history, conflict resolution drafts, discard recovery copies, settings snapshots, practice repositories and more are now listed, with where they are kept and their retention limits. All of it stays on your device and is not sent to PALDYN. (Section 7.4)
  • Git settings Branch writes: your author name and email, signing settings and pull method are written to your Git configuration only when you save them in Branch. Setting up Git LFS in a repository writes its settings and creates a pre-push hook if there is none, and changing tracking rules edits .gitattributes. (Section 7.4, item 3)
  • Signature checks: when the details of a signed commit are shown, the signing program set in your Git configuration (gpg or ssh-keygen unless you set another) checks the signature on your device. Because the current commit is selected when a repository opens, this can happen without your choosing a commit, and depending on your GnuPG configuration, GnuPG may connect to a key server to find the signer's public key. (Section 7.3)
  • Saved sign-ins: a credential helper may connect to the remote service's sign-in and authentication addresses when it refreshes or checks a saved sign-in, and may delete a saved sign-in that the remote service rejects. This also applies during automatic Fetch, and the deleted item may be one that other Git apps use as well. (Section 7.3)
  • Also: downloading Git LFS content is now listed among the remote operations, and the temporary copies passed to external comparison and merge tools, and their deletion, are described. (Sections 7.3 and 7.5)

PALDYN still does not collect your information through the Software, and the Software stays free of charge during the Beta Period. If you keep using the Software after the effective date, you are deemed to have accepted the changes; if you do not accept them, you may stop using the Software and terminate this Agreement (Section 14.3).

7. Data practices

  1. PALDYN does not use the Software to collect your personal information, repository contents, files, commits, credentials or usage history, or to send them to PALDYN's servers. The Software contains no usage analytics, telemetry, advertising or crash reporting.
  2. Updates and author photos. The only network communications that the Software starts without your request are the update check and the automatic update download described in Section 6.2, the author photo requests described at the end of this paragraph and, only if you turn it on in the settings, the automatic Fetch described at the end of paragraph 3. Update checks and update downloads use HTTPS only and request the update information file and update files that PALDYN publishes in its public paldyn/Branch-releases repository on GitHub (github.com, operated by GitHub, Inc.). These requests contain no user identifier, account information or repository information added by the Software. As with any internet request, however, ordinary request information such as your IP address, the time of the request and the updater's identification string (User-Agent) reaches GitHub and is handled under GitHub's privacy statement. PALDYN can see the aggregate download count of each file that GitHub provides, which does not identify individual users. While "Author photos" is turned on in the settings (it is on by default), the Software loads, over HTTPS through its built-in web view, the photo of each commit author it shows: when the author's email address is a GitHub no-reply address (number+name@users.noreply.github.com), from GitHub (avatars.githubusercontent.com), sending only the account number in that address; for any other author email address, from Gravatar (gravatar.com, operated by Automattic Inc.), sending only the SHA-256 hash of that email address. These requests contain nothing else added by the Software. The hash does not make the email address anonymous, however: Automattic can recognize addresses registered with Gravatar, and anyone who knows or guesses an address can compute its hash and match it. Ordinary request information, such as your IP address, the time of the request, and the web view's identification string (User-Agent) and language preferences, reaches GitHub or Automattic with each request and is handled under their privacy statements, so these services can tell which commit authors are being viewed from your connection. Turning off "Author photos" in Settings → Appearance stops these requests.
  3. Git remote operations. Git remote operations, such as cloning, fetching, pulling, pushing, listing remote references (including the connection check in Settings → Git), adding or updating submodules and downloading Git LFS content, run only when you request them, except for the automatic Fetch described at the end of this paragraph. The Software performs them by running a Git program (the Git included with the Software or, if you choose it in the settings or the included Git cannot run, the Git installed on your computer) and connects only to remote addresses that you enter or that are configured in the repository, including submodule addresses. The permitted transports are file, https, http, ssh and git. Authentication is handled by your Git configuration, SSH keys and credential helpers; the Software itself does not store passwords, tokens or other credentials. When the included Git is used on macOS, the macOS keychain credential helper of Git that is included with the Software is configured by default (your Git configuration can replace it). Like the helper of Apple's Git, it stores the HTTPS credentials with which Git has signed in successfully in the login keychain on your computer and reads them from there. On Windows, the Git Credential Manager contained in the Git included with the Software is configured as the default credential helper (your Git configuration can replace it). When a remote operation needs HTTPS authentication, Git Credential Manager uses the sign-in information it has stored (refreshing or checking it when needed) and, for a remote operation you requested, runs the remote service's sign-in in your default browser or in its own window; in doing so it may also connect to the addresses that service uses for sign-in and authentication (for example GitHub's API address, or the Microsoft account sign-in address for Azure DevOps). Git Credential Manager stores the sign-in information (tokens or passwords) in Windows Credential Manager on your computer and reads it from there, the same store that the Git Credential Manager of a Git for Windows installed on your computer uses. On either operating system, these credentials are not sent to PALDYN. If you include credentials in a remote address, however, Git may record that address in the repository configuration. Information exchanged with a remote service (for example GitHub, GitLab, Bitbucket or Azure DevOps) is subject to that service's terms and privacy statement. Git behaves as your Git and repository configuration directs, for example when running Git hooks or when Git automatically downloads missing objects in a partial clone. This includes checking the signatures of commits and tags: when the details of a signed commit are shown in the commit history or you open the signature check of a tag, the Software has Git run, on your device, the signing program set in your Git configuration (unless you set another, GnuPG's gpg for OpenPGP signatures and ssh-keygen for SSH signatures) to check the signature. Because the Software selects the current commit automatically when a repository opens and after operations such as switching branches, this check can take place without your choosing a commit. The Software adds no communication of its own to this check, but depending on your GnuPG configuration (for example auto-key-retrieve or key server settings), GnuPG may connect to a key server or a similar service to find the signer's public key. The Software re-reads repository status periodically, and when it notices changes in the folder of the repository you are viewing, to keep its display current, but it does not run Git commands that contact remote repositories, such as fetch, for this purpose. However, when you choose an interval for "Automatic Fetch" in Settings → Git (it is "Off" by default, and the intervals range from 1 to 60 minutes), the Software, while it is running and without any further request, fetches at that interval from all remote repositories configured in each repository that is open in the current workspace and for which automatic Fetch has not been turned off, one repository at a time (git fetch --all --prune; "automatic Fetch"). Automatic Fetch connects only to the remote addresses configured in those repositories (including, when a credential helper such as Git Credential Manager refreshes or checks a saved sign-in, the addresses that remote service uses for sign-in and authentication), uses only credentials that are already saved, and the Software shows no sign-in window or prompt for it. macOS may, however, ask whether to allow access the first time the included Git reads credentials that another Git saved in the keychain, and credential helpers or SSH agents that you set up yourself may ask for confirmation as you configured them. If a remote service rejects a saved sign-in, Git may have the credential helper delete that sign-in, also during automatic Fetch, and the deleted item may be one that other Git apps use as well (in the login keychain on macOS, or in Windows Credential Manager on Windows). A remote repository that needs a new sign-in is not fetched automatically, and the failure is recorded in the Activity center. Automatic Fetch does not change your working files or local branches; it updates remote-tracking branches (removing those of branches deleted on the remote) and may add tags that point to fetched commits. Choosing "Off" for "Automatic Fetch" in Settings → Git stops automatic Fetch, and a repository you untick in the list there is not fetched automatically.
  4. Information stored on your device. The Software stores the following information only on your device and does not send it to PALDYN:
    1. settings (such as theme, accent color, language, keyboard shortcuts, the update settings, the external editor you chose, which is an application name or the path of an application you selected, the comparison and merge tools you chose, the automatic Fetch interval and the path of the default work folder in which the Software looks for repositories), workspace information (local paths of the repositories you opened, tabs, groups and, for repositories brought over from a backup, their remote addresses), the version and release notes of an Update recorded right before it is installed (used to show release notes after the restart; this temporary entry is deleted once shown or no longer needed), the most recently installed version's release notes retained for reopening in Settings regardless of the automatic-popup setting (replaced by the next installed version's notes and excluded from backups), and, for each repository, commit message drafts in progress, layout, the order of local branches, the names of recently used local branches, whether automatic Fetch is on, the name of the branch to return to after you check out a specific commit, and the commit ID at which a detached HEAD began: in the local storage of the Software's built-in web view (on macOS, ~/Library/WebKit/com.paldyn.branch/; on Windows, %LOCALAPPDATA%\com.paldyn.branch\EBWebView\);
    2. window position and size, the choice of Git executable, the system-level Git configuration generated for the included Git, the settings snapshots saved automatically with the current settings before a backup is imported or earlier settings are restored (the newest 5 are kept), and the practice repositories created by the guides: in .window-state.json, git-executable.json, bundled-git/gitconfig, backups/ and practice/ in the application settings folder (on macOS, all in ~/Library/Application Support/com.paldyn.branch/; on Windows, .window-state.json in %APPDATA%\com.paldyn.branch\ and the rest in %LOCALAPPDATA%\com.paldyn.branch\);
    3. Git settings values: your Git author name and email, the signing settings for commits and tags (gpg.format, user.signingkey, commit.gpgsign, tag.gpgsign, gpg.ssh.allowedSignersFile) and the pull method (pull.rebase), written to your Git configuration (global or for the repository) only when you save them in the Software. When you set up Git LFS in a repository, the Software writes the Git LFS settings (filter.lfs.* and lfs.repositoryformatversion) to that repository's configuration and, if the repository's Git folder has no hooks/pre-push, creates Git LFS's pre-push hook, which uploads Git LFS content when you push; when you add or remove a Git LFS tracking rule, it edits the .gitattributes file at the top of the repository (like any other file, it reaches remote repositories when you commit and push it). So that you can choose a signing key, the Software reads, on your device, the names of the public key files (.pub) in your ~/.ssh folder (on Windows, %USERPROFILE%\.ssh\); it records a name, as the user.signingkey above, only when you choose that key as your signing key and save it, and it never sends the key files' names or contents;
    4. temporary working files needed for an interactive rebase: inside that repository's .git folder;
    5. recovery references: before a reset, a rebase or an interactive rebase, the Software records the commit that HEAD points to, and before it deletes a branch or tag in a remote repository, it first fetches the commit or tag that the remote branch or tag points to. Before a force push, it records the remote commit confirmed for replacement. It keeps each of these in that repository as a Git reference under refs/branch/recovery/, with a reflog entry, so that the previous state can be recovered. When a new checkpoint is created, the Software keeps the newest 20 references it can identify as its own or those created less than 14 days ago; older references that satisfy neither condition are eligible for automatic cleanup. It does not automatically delete references used by active sessions or references it cannot identify as created by the Software, and it skips cleanup if it cannot read session information from any worktree of the repository. Some references may therefore remain longer. You can also delete them yourself, for example with git update-ref -d <reference name>, or all at once with git for-each-ref --format='delete %(refname)' refs/branch/recovery/ | git update-ref --stdin. While they remain, Git's garbage collection does not remove the commits they point to, even after a reset has removed those commits from your branches. Ordinary pushes and clones do not transfer these references, but commands that copy every reference of a repository, such as git push --mirror or git clone --mirror, do;
    6. if settings saved under the identifier of an earlier version exist, the Software copies them to the new location on your device the first time it runs;
    7. author photos loaded under paragraph 2 and their addresses, which contain the email hashes or GitHub account numbers: in the built-in web view's cache (on macOS, ~/Library/Caches/com.paldyn.branch/; on Windows, inside %LOCALAPPDATA%\com.paldyn.branch\EBWebView\). They can remain there after you turn off "Author photos";
    8. activity history: the results of the Git operations you run and of automatic Fetch (the repository's name and local path, the command run, the outcome and Git's output; parts of the output that look like credentials, such as passwords and tokens, are masked before saving): in the built-in web view's local storage (the location in item 1). Entries older than 30 days are deleted, at most the newest 100 of your own operations and the newest 50 automatic Fetch results are kept, about 512 KB in all, and the history is excluded from backups;
    9. conflict resolution drafts: the choices and edits you have not yet saved in the conflict resolution view, including the contents of the conflicted file: in the built-in web view's local storage (the location in item 1). The Software deletes a file's draft when you save the file and all drafts of a repository when it sees that the repository's conflicts have ended, and deletes drafts last changed more than 14 days ago the next time the conflict resolution view opens. All drafts together are kept within about 2 MB (beyond that, the oldest are deleted first), and they are excluded from backups; and
    10. discard recovery copies: before you discard files or selected changes, and before restoring a historical version over a working file that holds content Git does not have, the Software saves the full contents of the files being discarded or replaced, and their staged contents, as a recovery copy (except when the changes are too large and you choose to discard without one): in branch/discard-recovery/ inside the Git folder of that worktree (for example .git/branch/discard-recovery/). Each copy holds at most 64 MB and all copies together at most 256 MB; up to the newest 50 completed copies are kept for 30 days, and when space is needed, copies already restored and then the oldest are deleted first. Copies of a discard that was interrupted are not deleted automatically. Recovery copies are never pushed to remote repositories and are left out of the Software's repository backups; they are deleted when you delete them in the "Restore discarded changes" window or delete the repository.

    This information may remain on your device after you delete the Software. You can delete the files in the locations above, and the recovery references in item 5, yourself; you can also clear the activity history in item 8 with "Clear completed history" in the Activity center and delete the recovery copies in item 10 in the "Restore discarded changes" window. On Windows, if you choose to delete the application data when you uninstall the Software, the folders %APPDATA%\com.paldyn.branch\ and %LOCALAPPDATA%\com.paldyn.branch\ above are deleted with it.

  5. Other local integrations. When you ask it to, the Software opens a repository in Finder, Terminal or the external editor you choose in Settings → External apps (Visual Studio Code unless you choose another application), opens the official release notes page in your default browser, copies text to the clipboard and opens file selection dialogs. On Windows, it opens File Explorer instead of Finder and Windows Terminal instead of Terminal. Previews of repository contents, such as image previews, are processed entirely on your device. When you open a selected file in a comparison or merge tool chosen in Settings → External apps, the Software makes temporary copies of the relevant file versions in the operating system's temporary folder, passes them to that installed application and deletes them when the comparison or merge ends (when you close it in the tool or cancel it in the Software). If you quit the Software while the tool is still open, the copies can remain in that folder. A merge result returns to the Software as an unsaved draft for review.
